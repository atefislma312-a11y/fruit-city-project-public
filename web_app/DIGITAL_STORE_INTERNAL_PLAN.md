## الهدف والأولوية
إكمال البنية التشغيلية لمنيو العملاء والطلبات داخل Fruit City كـ«فرع رقمي» متصل بالكاشير والمخزون عند اعتماد التكامل، **قبل** تجميل الواجهة. تأجيل اختيار شركة الدليفري وربطها؛ تصميم واجهة توصيل قابلة للتبديل دون الاعتماد على مزود واحد. لا شراء أو نشر أو تغيير في الإنتاج بهذه الخطة.

## المعمارية المستهدفة
1. **واجهة العميل:** كتالوج، أقسام وبحث، أحجام وكميات وإضافات بعد اعتمادها، سلة، استلام من المحل/توصيل، معلومات العميل والعنوان، عرض أسعار ورسوم مؤكدة، إرسال ومتابعة الحالة.
2. **خدمة الطلبات الموثوقة:** API يتحقق على الخادم من SKU والحجم والكمية والتوافر والسعر والرسوم قبل تثبيت الطلب؛ رقم طلب موحد + مفتاح idempotency؛ حفظ دائم وإيصال استلام تقني منفصل عن قبول المحل؛ سجل أحداث/Audit بلا أسرار.
3. **مركز طلبات الكاشير:** صندوق استقبال، قبول/رفض بسبب مسجل، تقدير وقت التحضير، انتقال للتحضير ثم جاهز ثم مسلَّم/مغلق، وإلغاء/هالك/استرداد بصلاحيات. لا حذف لطلب مدفوع أو إخفاء تاريخه.
4. **شاشة التحضير:** طابور أو تذاكر عمل تُنشأ عند قبول الطلب فقط، حالات قيد التحضير/جاهز، ومراجعة الأصناف لتجنب النقص.
5. **لوحة المدير:** إدارة المنتجات والأسعار والتوافر والساعات والقدرة التشغيلية ووقف الطلبات، إدارة المستخدمين والصلاحيات، متابعة الطلبات والتسويات والتقارير.
6. **الدفع والتحصيل:** تصميم قابل للتوسعة؛ بداية مقترحة كاش عند الاستلام وإنستا باي يدوي **مع تحقق فعلي من الحركة** وليس اعتماد صورة، ثم روابط/بوابة دفع بعد مراجعة التكلفة والتعاقد. فصل حالة الطلب عن حالة الدفع وحالة التسوية. أية وسيلة لم تُعتمد نهائيًا بعد.
7. **المخزون والتقارير:** الربط بالوصفات والخامات والهالك بعد تدقيق نظام الإدارة القائم ومصدر الحقيقة؛ عدم بناء مصدر متنافس للأرصدة. تقارير الطلبات والقنوات والإلغاءات والتسويات وهامش الربح عند توفر بيانات تكلفة معتمدة.
8. **الدليفري (مؤجل التفعيل):** واجهة Provider مستقلة تدعم مندوب المحل أو شركة خارجية لاحقًا؛ تحصيل العميل/المندوب/المحل والتسويات تتحدد بعد عروض الشركات. متطلبات نطاق 5 كم والخرائط محفوظة في `OPERATING_REQUIREMENTS.md` ولم تُنفذ.

## قواعد التشغيل الأساسية
- طلب واحد برقم واحد من جميع القنوات، ولا يتحول إخطار واتساب إلى طلب بيع مكرر.
- طلب محفوظ != طلب مقبول != تجهيز بدأ != دفع مؤكد.
- مصدر معتمد للأسعار والتوافر مع نسخة سعر مثبتة (snapshot) لكل أوردر عند التأكيد؛ لا اختلاق أسعار.
- عند توقف المحل/انقطاع الإنترنت: الطلب محفوظ «بانتظار قبول»، ومنع إعادة الإرسال المكرر، مع خيار إيقاف استقبال الجديد عند عدم القدرة.
- لا يبدأ تجهيز إنستا باي قبل التحقق الموثوق من التحويل وقبول الطلب؛ سياسة الكاش والإلغاء تحتاج اعتماد.
- سجل تدقيق لكل تغيير جوهري، وضوابط صلاحيات، وعدم نشر بيانات شخصية/أسرار/قاعدة الإنتاج على GitHub.
- عدم فتح قاعدة البيانات المحلية للإنترنت وعدم الكتابة مباشرة في `sql.js` الإنتاج؛ التكامل يتم عبر واجهة خادم الكاشير المالك للكتابة بعد فحص قراءة فقط.

## حالات الطلب المقترحة
`draft -> submitted -> pending_store_acceptance -> accepted -> preparing -> ready -> handed_off -> completed`
وفروع `rejected` و`cancelled` مع سبب مسجل؛ المدفوعات لها مسار منفصل `unpaid / pending_verification / paid / refund_pending / refunded`، والتسوية منفصلة كذلك. المخطط يحتاج تدقيق هندسي قبل اعتماده برمجيًا.

## مراحل التنفيذ المطلوبة والقبول
1. **جرد توافق قراءة فقط:** مقارنة كتالوج الويب مع أصناف الكاشير ومصدر الأسعار والتوافر وواجهات الخادم ومسار البيانات والصلاحيات؛ توثيق الفجوات، دون نقل كود POS أو تعطيل عملياته.
2. **خدمة طلبات معزولة:** تصميم عقد API ومخطط البيانات والاختبارات الآلية؛ إنشاء طلب تجريبي مرة واحدة رغم إعادة الإرسال، وتحقق السعر والتوافر وحالات الشبكة؛ بدون أي كتابة لقاعدة الإنتاج.
3. **لوحة استقبال/تحضير وصلاحيات:** اختبار قبول ورفض وإلغاء وتغيير حالة طلب وتسجيل من فعل ذلك، ثم ربط آمن عبر API المعتمد بعد تفويض منفصل.
4. **الدفع والتسوية:** سجلات مستقلة، تحقق يدوي آمن لإنستا باي، إعادة محاولات بدون ازدواجية، سياسات المرتجع، واختبارات التسوية.
5. **المخزون والتقارير:** التكامل الآمن بعد تدقيق نظام الكاشير، واختبارات منع الخصم المكرر، ثم التشغيل التجريبي بنطاق محدود.
6. **اختبارات الإطلاق:** انقطاع الشبكة، الازدواجية، الضغط وأوقات الذروة، صلاحيات المدير والكاشير، أمان بيانات العميل، ثم نشر بعد موافقة؛ تحسين الصور/التصميم والـSEO لاحقًا.
